# ADR 0016: Retire DynamoDB Terraform state locking only after a controlled S3 lockfile transition

**Status:** Proposed
**Decision date:** 2026-09-20

## Context

The target state-backend module currently emits both S3 lockfile and DynamoDB
lock-table configuration. DynamoDB locking remains for the legacy bootstrap and
as a compatibility bridge; it must not be removed merely because source code
can emit `use_lockfile = true`. Removing a lock mechanism while an operator or
pipeline can still use it risks concurrent state mutation.

## Decision

1. New backend configurations may enable the S3 lockfile only through the
   approved backend configuration generated by the state module.
2. DynamoDB lock-table removal is forbidden until every consumer’s backend
   configuration and Terraform version are inventoried, a non-production
   concurrency test has passed, a no-change migration plan is reviewed, and a
   restore drill is accepted.
3. The change must have Cloud Architecture, Security, SRE, and
   Platform/DevOps approval; it must include a rollback to the known working
   backend configuration and a final lock-table activity check.
4. The lock table remains protected from Terraform destruction throughout the
   transition. A separate ADR amendment will record the evidence and authorize
   deletion only after the retirement window closes.

## Consequences

- Backend output can remain compatible with both lock mechanisms during the
  transition without suggesting they are interchangeable in production.
- No state lock-table cleanup is automated by CI or by a normal Terraform
  apply.
- The transition is an operational change with evidence, not a refactor of
  backend strings.
